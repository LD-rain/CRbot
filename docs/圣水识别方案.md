# 对局内逻辑与圣水识别方案

> 目标：在 720×1280 的《皇室战争》国服对局里，稳定读出**当前圣水**和**哪几张手牌能打**，
> 让机器人能在对局中持续出牌，并把对局开始/结束接进已有的主循环。
>
> 本文给出 5 种可选方案、它们的取舍、最终选型，以及在本项目里落地后的实测数据。

## 1. 先说结论

| 方案 | 思路 | 精度 | 速度 | 依赖 | 结论 |
|---|---|---|---|---|---|
| **A 像素比例法** | 定位底部圣水条，数"亮格" | 整数、无误差 | <1ms | 无 | ✅ **采用** |
| B 数字 OCR | 认条左侧的大号白色数字 | 整数，偶发认错 | 200~500ms | Windows OCR | 作为校验，不作主用 |
| C 时间模型 | 按 2.8s/点圣水推算 | 会漂移 | 0 | 无 | ✅ **作为兜底/滤波** |
| D 模板匹配 | 匹配 10 个刻度、前沿辉光 | 高但要标定素材 | 快 | 每版本模板 | 备用（换皮肤/改版时） |
| E 读内存/注入 | 直接读游戏内存 | 完美 | 快 | root/注入 | ❌ 不可行且风险高 |
| F 深度学习 | 分割/检测圣水条 | 高 | 慢 | 训练数据 | ❌ 过度设计 |

最终实现是 **A 为主 + C 兜底 + B 可选**，并且额外用一个"卡牌压暗"特征绕开了"知道每张牌费用"的需求。

## 2. 为什么圣水识别值得单独设计

皇室战争对局底部的这根条有几个坑：

1. **它不是纯色进度条**：空槽是深蓝 `(2,52,120)`，填充是品红 `(238,84,243)`；
   升级/出牌瞬间会有 3~8 帧的**脉冲动画**（填充变白 `(255,157,255)`，前沿冲过头几像素）。
2. **它会被动画整条遮住**：出牌瞬间有约 0.1~0.3s 的白光闪过，这一帧怎么读都是错的。
3. **它左边压着一个大号白色数字**，会盖住第 1 格的填充；条底部还有"最多：10"小字。
4. **没有对局外的参照**：主界面底部是另一套 UI，所以"圣水条在不在"本身就是最好的
   "是否在对局中"判据（比 OCR 找文字快得多、稳得多）。
5. 双倍圣水 / 加时赛只改变**回复速度**，不改变条的画法，所以读条不受影响。

因此一个能用的读数器必须做到：**定位固定、颜色判据对动画鲁棒、读不出来时能退回上一个值**。

## 3. 实测几何（720×1280，来自录像帧）

用一段 2842 帧的对局录像（MuMu 共享目录 `VideoRecords\frames`，逐帧 PNG）逐像素量的结果：

```
 y=1236 ┌──────────────────────────────────────────────────────┐
        │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  ← 已填充 (238,84,243)            │
        │ ░░░░░░░░░░░░░░░░░░░░  ← 空槽   (2,52,120)            │
 y=1262 └──────────────────────────────────────────────────────┘
        x=195                                               x=695
        └──── 10 格 × 50px ────┘
```

| 量 | 值 |
|---|---|
| 条范围 | x 195 → 695（宽 500px） |
| 格数 | 10，每格 **50px**（刻度实测在 245/295/345/395/445/495/545/595/645，误差 ≤1px） |
| 采样带 | y **1238…1258**（避开上下圆角和 y≈1265 的"最多：10"） |
| 填充色 | `(238, 84, 243)`，脉冲时可达 `(255,157,255)` |
| 空槽色 | `(2, 52, 120)`，被霓虹描边时 `(54,87,160)` |
| 手牌 4 格 | x `[175,300] [305,430] [435,560] [565,690]`，卡面 y 1080…1160 |

代码里这些都以**归一化比例**保存（除以 720/1280），换成别的分辨率不用改代码——
`ElixirBar default_elixir_bar(w, h)` 自动换算。

## 4. 判据（就是全部算法）

### 4.1 圣水

逐列统计采样带内的像素：

```cpp
// 填充：R、B 都亮，G 明显偏低 → 品红。纯白 (255,255,255) 不满足，不会把闪光当满圣水，
// 而且 R/B 顺序无关（有的机型截图是 BGRA）。
bool is_fill(p)  { return p.R>=100 && p.B>=100 && p.G <= min(p.R,p.B)*0.85; }
// 空槽：很暗的蓝。前沿辉光 (54,87,160) 最亮通道 160 也被算作空槽，正好把"头"卡准。
bool is_empty(p) { int mx=max3(r,g,b), mn=min3(r,g,b); return mx>=80 && mx<=190 && mn<=70; }

列填充率 = 该列满足 is_fill 的行数 / 采样行数
最后一列填充率 > 50%  → 这就是填充前沿 head_x
segments = round((head_x + 1 - x0) / 50.0)      // 0…10
```

**为什么用"最后一列"而不是"数格子"**：数字"10"压在条上，第 1 格永远读不全；
从左往右数会错，从右往左找前沿则完全不受影响。

### 4.2 这条条到底在不在（= 是否在对局中）

```cpp
bar_like = 满足 (fill+empty) ≥ 90% 采样行的列数
visible  = bar_like ≥ 80% 的总列数
```

阈值 80% 是实测卡出来的：**对局帧占 91.8%~97.4%**（满圣水时左边两位数"10"会多盖几列，
所以最低 91.8%），而菜单/登录页只有约 20%。两边余量都很大。
主界面、结算界面、商店等画面这一带是别的 UI，`bar_like` 会掉下去 → `visible=false`。
实测 2842 帧里 2830 帧可见，剩下 12 帧全部是"出牌瞬间的白光动画"——交给时间模型兜底即可。

### 4.3 手牌能不能打（关键取巧点）

**游戏自己会把圣水不够的卡压暗**，所以不需要知道卡的费用、也不需要知道卡组：

| 状态 | 判据（卡面区域的饱和度均值 / 亮度标准差） | 实测区间 |
|---|---|---|
| 空卡位（刚打出） | `stddev < 25` | 12 ~ 14 |
| 圣水不够 | `sat < 0.22` | 0.03 ~ 0.13 |
| **可以打** | 其余 | 0.33 ~ 0.74 |

两个阈值都落在 2 倍以上的空隙里，不是勉强卡出来的。用 406 帧 × 4 格做回归：
`零圣水时误判为可打` 只有 4 次（且全部发生在白光动画那 1 帧）；`满圣水时误判为不可打` 0 次。

## 5. 动画/误读怎么兜（这是实践中最关键的一段）

| 现象 | 处理 |
|---|---|
| 出牌瞬间整条白光，读数乱跳 | **下降立即采信、上升受时间约束**（每帧最多涨 `dt秒 + 1` 格）；出牌后 9→1 这种大跌立刻生效 |
| 读数与手牌自相矛盾 | 交叉校验：圣水说够、四张牌却全灰 → 本帧不出牌（多半是扣费动画里的假高值） |
| 脉冲把前沿冲过 3~4px | 单元本来就取整到格，取整天然吸收 |
| 条被动画遮住 1~2 帧 | `visible=false`，不覆盖上一个读数；连续 >4s 才认定**本局结束** |
| 手牌刚打出、卡位空着 | `CardState::Empty`，这一格不打（否则第二下点击会落到空地上） |
| 截图偶尔失败 | 记录日志、下一轮重试，不中断对局 |

> **踩过的两个坑**：
> 1. 最早用"连续两帧读数相同才采信"。双倍圣水时读数一直在涨，出牌后 9→1 这种大步下跌
>    永远等不到相同值，读数**卡死在 9**——表现就是"手牌全灰但显示 9 费"，并会连下两张。
> 2. 换成"最近 3 帧中值滤波"后仍然不行：单帧就要 1.4 秒，等 3 帧滞后近 3 秒，
>    出牌后的假高值反而被当成真值采信。
>
> 最终方案是**有方向性的滤波**：下跌无条件采信（扣费是即时的），上升才受时间约束。
> 再叠加"手牌交叉校验"和出牌后的 `play_interval_ms`，才彻底稳住。

### 6.1 两个循环的边界

```
BotRunner::run()                          ← 一条设备线程的生命周期
  ├─ setup: 启动游戏 / 等登录 / 选经典1v1
  └─ while (!stop) {                      ← 对局外循环
        nav.start_match()                 （点"对战"，只负责开）
        Battler b(device, sink, stop)
        b.wait_for_start()  ── 圣水条出现 ──→  对局内开始
        b.run()             ── 圣水条消失 4s ─→  对局内结束
        nav.finish_match()                （结算点掉，回主界面）
     }
```

* **进场/出场各只有一个信号**：圣水条可见 / 消失 ≥4s。两侧都不用 OCR，
  所以对局内（纯像素）和对局外（模板匹配）的时基完全独立。
* `Battler` 不认识 `DeviceState`，只通过 `BattleSink` 播报
  `BattleTelemetry{phase, elixir, hand, played, elapsed_ms}`，GUI 文案由 `BotRunner` 组装。
* `Navigator` 只剩三个原子操作（`navigate_to_1v1` / `start_match` / `finish_match`），不再编排整局。
* 对局外循环带退避重试：开场或收尾连续失败 3 次才把这条设备线程标记为 error。

对局主循环（`Battler::run`）伪代码：

```
while (!stop) {
    img = device.screenshot()                    // PNG，~200-600ms/帧，天然限速
    r   = read_elixir(img, bar)
    if (!r.visible) { if (4s 没看见条) return 本局结束; continue; }
    seg = 滤波(r.segments)        // 下降立即采信；上升每帧最多 dt秒+1 格
    手牌 = read_card(4 格)
    telemetry(seg, 手牌)                          // 播报给上层
    if (圣水够 但 四张全灰) 跳过本帧             // 交叉校验，防假高值
    else if (seg >= 阈值) 且 距上次出牌 >= play_interval_ms:
        阈值 = 前 117s ? 9 : 8                 // 双倍圣水后降到 8，避免溢出
        选牌：优先 Ready；双倍阶段允许挑"还灰着"的
        点卡 → 点 (360,695) → 记下出牌时刻
}
```

策略参数都在 `BattleConfig`（`include/battler.h`）里：

| 参数 | 默认 | 含义 |
|---|---|---|
| `early_elixir` | 9 | 前 117 秒的出手阈值 |
| `late_elixir` | 8 | 双倍圣水阶段的出手阈值 |
| `late_after_ms` | 117000 | 多久后切到双倍节奏 |
| `late_play_dim` | true | 双倍阶段允许提前下"灰卡" |
| `deploy_x / deploy_y` | 360 / 695 | 落点 |
| `tap_gap_ms` | 120 | 选牌 → 落点之间，给游戏确认选牌 |
| `tap_settle_ms` | 180 | 落点之后，给游戏处理落点/扣费 |
| `play_interval_ms` | 600 | 两次出牌的最小间隔（兜底） |

**时序约定**：下一次截图必须发生在「`input tap` 的 adb 进程已退出」**并且**
「游戏已经把落点和扣费处理完」之后。

* 前半句靠阻塞：`run_process` 会等 adb 进程退出，所以 tap 返回即代表事件已注入；
* 后半句靠 `tap_settle_ms`：命令返回只说明事件进了输入队列，游戏还要一帧才处理。

**为什么不再"等圣水下降"**：游戏里下牌→扣圣水是即时的（录像里一帧就掉下去了）。慢的是
我们这边——每次 `screencap` 要起 adb 进程、传几 MB 数据，单帧 300~900ms。
用读数做判据实际上是在等自己的截图周期，日志里那个 `spend confirmed after 4126ms`
就是等了两轮自己截图的产物。

连下两张的真正原因也不是扣费延迟，而是早期滤波把读数卡死在旧值上（见第 5 节）。
现在用**有方向性的滤波 + 手牌交叉校验 + `play_interval_ms`** 三重保证。

## 7. 实测结果

* **读数正确性**：抽 8 帧把"实测条数"和游戏大号数字对拍 —— 7↔7.02、2↔2.02、1↔1.06、
  3↔3.04、5↔5.02、6↔6.02、8↔8.02、10↔10，全部落在同一格。
  对比图：`tools/elixir_validation.png`
* **整段录像回归**：2842 帧，`elixir_probe` 逐帧输出 CSV，`visible=2830`，
  非对局帧只有出牌闪光那 12 帧；圣水曲线呈标准锯齿（涨到某值→出牌回落）。
* **手牌回归**：406 帧抽样，零圣水时"全暗"、满圣水时"全亮"，误判 4 次（同一帧的闪光）。

## 8. 实机验证过的东西 / 还要留意的

* **出牌点**：`BattleConfig::deploy_x / deploy_y`（默认 360 / 695，河边中央）已按录像帧量好；
  换分辨率才需要改。
* **结算 / 奖励界面**：靠"确定"模板 + 空白处点击推进，实机跑通；
  遇到赛季专属活动页（纯动画、没有可匹配特征）时仍然只用空白点击，不会误触按钮。
* **卡住时**：程序会存 `crbot_debug.png` / `crbot_battle_<serial>.png`（真实 720x1280 帧），
  拿它就能直接量出按钮位置、补一个模板。

调试建议：日志里每帧的 `seg`、手牌状态、每次点击的坐标与匹配分都已打印，跑一局看日志即可定位。
